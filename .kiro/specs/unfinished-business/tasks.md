# 任务页：Unfinished Business

依据 `requirements.md` 与 `design.md`（均为 2026-11-07 修订版）。本页取代旧任务页的阶段划分。实施顺序改为“可玩纵向切片优先”：先让房子立起来，再让第一只幽灵入住并走完主线，之后才做持久化、坏存档恢复、完整双语、完整无障碍与发布收口。

## 执行规则

- **主线优先**：阶段 1 至阶段 5 组成可玩主线。阶段 3 结束时房子完整立起来；阶段 4 结束时第一只灰色幽灵入住；阶段 5 结束时它走完整条主线并会做家务。坏存档恢复、完整双语、完整无障碍与发布收口全部排在主线之后。
- **三个发起人里程碑，且仅三个**：
  - A：阶段 3 末尾，房子第一次完整立起来。
  - B：阶段 5 末尾，第一只幽灵完整走完主线并会做家务。
  - C：阶段 17，发布前的总体验。
  其余检查全部由自动测试或实现者在浏览器中的检查完成，不阻塞在发起人身上。
- **发起人的动作只有两种**：看画面后回复“可以”，或指出某个位置往哪挪。发起人不测数值，不改存档，不跑命令，不补截图或动图。
- **位置与坐标由 Kiro 自行确定**：门厅纪念册目标点、12 盏暖灯候选位、楼层的可导航区、障碍矩形、Home Anchor 与动作位，都从 `public/assets/dollhouse/atlas.json`、`room-layout.json` 与素材本身派生，并在开发者校准层中画出来核对。派生不出来的位置保持关闭状态，不写入估算值。
- **开发者校准层只在开发模式存在**（`import.meta.env.DEV`）。生产构建中不得出现校准层代码、调试标记或其入口字符串，由 15.2 的测试检查构建产物。
- **浏览器检查统一由 Playwright 脚本断言完成**。实现者可以用截图辅助排查，但验收依据是脚本断言，不是手工点击。
- **编号约定**：`R` 指 requirements.md 的需求编号；`P` 指 design.md 的 Correctness Properties 编号。每个任务列出目标、产物、验收、依赖与需求映射。
- **每个任务完成后运行 `npm test`**；每个阶段结束前运行 `npm run build` 与 `npm run test:e2e`，全部通过才进入下一阶段。

## 脚本与运行时机

| 命令 | 用途 | 何时运行 |
|---|---|---|
| `npm run dev` | 开发服务器。校准层只在此模式出现 | 阶段 3 起，需要给出预览地址时 |
| `npm run build` | 先 `tsc --noEmit`，再 `vite build` | 每个阶段结束前；提交前 |
| `npm run preview` | 预览生产构建 | 手动查看生产构建 |
| `npm test` | Vitest：单元、属性、组件与源码安全扫描（不含 `e2e/`） | 每个任务完成后 |
| `npm run test:e2e` | Playwright：先执行构建，再由配置启动预览服务并运行 `e2e/` 下的浏览器脚本 | 每个阶段结束前；每个里程碑前 |
| `npm run test:e2e:install` | 下载 Playwright 的 Chromium | 首次配置，或升级 Playwright 后执行一次 |

依赖清单：运行时只有 `preact`。开发依赖：`vite`、`@preact/preset-vite`、`typescript`、`vitest`、`fast-check`、`@testing-library/preact`、`happy-dom`、`@playwright/test`。版本精确锁定。本项目不使用 ESLint，设计中的 lint 规则由任务 1.3 的 Vitest 源码扫描承担，因此不存在 lint 命令。

目录约定：`src/` 为产品代码；`tests/` 为 Vitest 测试；`e2e/` 为 Playwright 脚本；`public/assets/dollhouse/` 为静态旧宅素材。

### 1.3 源码安全扫描（替代 ESLint）

- **目标**：用测试禁止危险写法与外部请求，保持设计中的安全约束。
- **产物**：`tests/source-safety.test.ts`，扫描 `src/` 下的文本文件：

  - 组件文件（`src/components/`）中不得出现含中文字符的字符串字面量，玩家可见的中文只能放在 `i18n/zh-CN.ts`。
  - 扫描逻辑对字符串做判定，测试内部用内存样例验证扫描器能抓到违规。测试不在磁盘上写入任何违规样例文件。
- **验收**：当前仓库扫描通过；内存样例中的违规写法都被判定为违规；磁盘上没有残留样例。
- **依赖**：1.2。
- **需求**：R1.3, R11.8, R12.2。

### 1.4 Playwright 基线与子路径服务

- **产物**：`playwright.config.ts`，webServer 为“构建后执行 `vite preview --port 4173 --strictPort`”；`e2e/helpers/subpath-server.ts`，用 Node 内置 `http` 把 `dist/` 挂在 `/unfinished-business/` 前缀下，不新增依赖；`e2e/smoke.spec.ts`，检查首屏可见、`h1` 唯一、页面没有非同源请求（用 `page.route` 记录）。
- **验收**：`npm run test:e2e` 通过根路径与子路径两条冒烟用例。
- **依赖**：1.2。
- **需求**：R12.3, R12.2。

**阶段 1 检查点（实现者）**：`npm run build`、`npm test`、`npm run test:e2e` 全部通过。

## 阶段 2 素材接入与布局数据

- **需求**：R6.10, R12.1, R12.8, R12.9。

### 2.2 ASSETS.md 初版

- **目标**：准确说明素材与原创内容的来源。
- **产物**：`ASSETS.md`，写清三类内容：
  1. 静态旧宅布景：屋顶、门厅与五个楼层模块的 PNG，由项目发起人根据团队原创描述，使用 ChatGPT 生成；由 Kiro 接入互动。运行时不修改图片内容。与布景同批提供的 `atlas.json` 与 `room-layout.json` 是这些布景的尺寸与锚点数据。

- **验收**：ASSETS.md 三类描述与上述一致；不写“全部原创”，不写“第三方素材为无”；不含本机路径与私人信息；游戏界面不显示这些来源说明。
- **依赖**：2.1。
- **需求**：R12.9, R12.8, R11.10。

### 2.3 素材映射模块 `assets.ts`

### 2.4 从 atlas 与 room-layout 派生布局数据

- **目标**：从两份 JSON 得到运行时数值。数值不手写，不估算。
- **产物**：
  - `src/house/data/modules.ts`：每个模块的逻辑宽度 801、高度、`topJoin`、`bottomJoin`、水平偏移 `dx`（初值取 design 的 `dx` 表）。
  - `src/house/data/slots.ts`：五层的 Home Anchor（左/右）、Home 参考范围（`room-layout.json` 的 left/right safe 小框，仅作出生/静止参考）、`meetY`。
  - `src/house/data/space.ts`：五层的 Room Navigable Rect/Polygon（`navigable`）、显式 Obstacle Rects（MVP 可为空，只登记代码里真实存在的互动家具或姿势道具，不把 Static_Layer 背景当障碍）、Action Spots（家务位、打招呼位、一起做家务位）。无法派生可导航区的层标 `missing`，该层 Ghost 只停在 Home Anchor，不写估算值。

- **验收**：`tests/house-data.test.ts` 读取两份 JSON 重新计算，与数据文件逐项相等；每层两个 Home Anchor 的 envelope 在 `navigable` 内且不碰 `obstacles`；两个 Home Anchor 间距不小于 148；每个动作位的 envelope 合法；数据文件不含“估算”“待定”等字样。若 JSON 与 design 的 Slot 表有出入，以 JSON 为准，并在里程碑 A 的汇报中列出差异。
- **依赖**：2.1，2.3。
- **需求**：R6.1, R6.5, R6.10。

### 2.5 静态堆叠纯函数 `layoutHouse`

- **需求**：R6.2, R6.10。

**阶段 2 检查点（实现者）**：`npm run build` 与 `npm test` 通过；素材复制完成后，`npm test` 中的存在性测试通过。

## 阶段 3 房子立起来

### 3.1 静态层组件与旧宅渲染

- **目标**：屋顶、门厅与楼层以 PNG 渲染，按 `layoutHouse` 堆叠，接缝无断裂。
- **产物**：
  - `src/components/StaticLayer.tsx`：入参类型只有 `grownFloors`。
  - `src/components/House.tsx`：组合夜空底色、`StaticLayer`，旧宅居中，按视口等比缩放（单列布局；镜头在阶段 11 接入）。首页传入 `state.house.grownFloors`（空房与前两只住客时只有门厅、一层住宅与屋顶），校准页仍可强制六层。
  - 图片：`alt=""`、`aria-hidden="true"`、`draggable="false"`、`pointer-events: none`，带 `width`、`height` 与 `srcset`、`sizes`；加载失败时显示纯色底板。
  - 静态层不接收任何 Task 数据，也不加滤镜或透明度变化。
- **验收**：类型测试确认 `StaticLayer` 的 props 只有 `grownFloors`。E2E 断言：`grownFloors` 为 6 时屋顶与六层模块全部渲染，相邻模块的边缘在屏幕上接缝误差不超过 1 CSS px；模拟某模块图片加载失败时显示底板，且没有未捕获异常。
- **依赖**：2.3，2.5。
- **需求**：R6.1, R6.9, R6.10, R11.7。

### 3.2 开发者校准层（仅开发模式）

- **目标**：Kiro 在一个画面里核对所有位置，发起人只看画面。
- **产物**：`src/dev/calibrate/Calibrate.tsx`，只在 `import.meta.env.DEV` 下通过 `#/calibrate` 访问。画面内容：
  - 每层完整的可导航区（Room Navigable Rect/Polygon）与当前真实存在的显式障碍/预留矩形，以及动作位；用不同颜色区分。Static_Layer 背景家具不画成障碍。
  - 每层 Home Anchor 十字与 Home Anchor 附近的出生/静止参考小框（来自 `room-layout.json` 的 left/right safe 小框），标签写作 “home L/R · rest zone”，**不得**叫整层安全活动区。
  - 门厅的纪念册目标点与热区（若 `archiveBook.status` 为 `missing`，则显示“未派生”标记且不画点）。
  - 12 个暖灯候选位，编号 1 至 12。
  - 静态灯占位区（虚线框）。
  - 楼层数切换按钮（2 至 6），用于强制显示完整六层。
  - 所有调试元素带 `data-debug` 属性，且只在开发模式渲染。
- **验收**：开发模式下 E2E 能打开校准层，看到 12 个灯位编号、五层的完整可导航区、障碍矩形、动作位与标为 home/rest zone 的小框；`npm run build` 后，`dist` 中不含 `calibrate`、`data-debug` 等标记，由 15.2 的测试检查。
- **依赖**：3.1。
- **需求**：R6.1, R6.7, R12.2（校准层不属于产品界面）。

### 3.3 派生纪念册目标点与 12 盏暖灯候选位

- **目标**：Kiro 自行确定纪念册飞入目标点与暖灯候选位，并用自动测试约束。
- **产物**：`src/house/data/lobby.ts` 的派生结果；`tests/lobby.test.ts`，检查：
  - 12 个候选位互不重合，间距不小于 24 单位；
  - 每个候选位的 x 位于 `wallAnchorsX` 的 `[34, 762]` 之间；
  - 候选位不与 `staticLampRects`（外扩 8 单位）以及 `archiveBook.hit` 相交；
  - `archiveBook.hit` 的尺寸不小于 44×44。
- **派生方法**：先从 `room-layout.json` 查找门厅中的书本与灯的锚点条目。找到则派生。找不到时，Kiro 在校准层中依据门厅 PNG 的亮暗分布与 `wallAnchorsX` 提出候选，并在校准层画出候选，由里程碑 A 核对。仍无法确定时，`archiveBook.status` 保持 `missing`，阶段 5 的飞行动画不启动。
- **验收**：测试通过；数据文件中没有手填估算值，每个数值都能指向派生来源（代码注释写明来源字段名）。
- **依赖**：2.4，3.2。
- **需求**：R5.2, R6.7。

### 3.4 Kiro 自检校准结果

- **目标**：交给发起人之前，Kiro 用 Playwright 检查校准画面的几何关系。
- **产物**：`e2e/calibration.spec.ts`，在开发服务器下运行（`playwright.config.ts` 中增加一个 `dev` 项目）。断言：
  - 每层可导航区、障碍矩形、动作位与 home/rest zone 小框都完全落在对应楼层盒子内；
  - 两个 Home Anchor 的 envelope 在可导航区内且不碰障碍矩形；
  - 校准层没有把 home/rest zone 小框标成整层活动区；
  - 12 个灯位与纪念册目标点的标号都落在门厅盒子内；
  - 校准层的调试框不超出舞台宽度（不出现水平滚动）。
- **验收**：测试通过。发现不通过的项，Kiro 修正数据派生后重跑；未修正前不进入 3.5。
- **依赖**：3.2，3.3。
- **需求**：R6.5, R6.9, R11.7。

## 阶段 6 本地持久化

### 6.1 `serializeSave` 与 `parseSave`

- **目标**：完整存档可以往返，非法输入不会抛出异常。
- **产物**：`src/persistence/serialize.ts`、`src/persistence/parse.ts`。`parseSave` 包住 `JSON.parse`，逐字段校验：`schema_version === 1`；字符串长度（标题 80、完成条件 200、留言 140、步骤 80）；步骤不超过 50；`ghostNo` 唯一；Slot 合法（楼层 2 至 6，slot 为 0 或 1），不重复，占用不超过 10；`grownFloors` 在 2 至 6，不小于 `floorsNeeded(占用数)`，每个 Task 的楼层不超过 `grownFloors`；`completedCount` 为非负整数且等于 `archive.length`；`lang` 合法；时间戳可解析。未知字段忽略。失败返回 `{ ok: false }`，永不抛出。
- **验收**：P10（往返）与 P11（非法输入不抛出异常）通过。超长字段、重复 Slot、`completedCount` 与 `archive` 不符，都返回 `ok: false`。

- **需求**：R9.2, R9.11。

### 6.2 存储适配器、防抖与降级

- **目标**：数据变更后保存，失败时不丢内存中的数据。
- **产物**：

- **验收**：使用假计时器测试：变更后 300 毫秒内写入，隐藏页面时立即写入；模拟写满后显示提示，且 state 不丢。

- **需求**：R9.1, R9.4。

### 6.3 启动只读加载

## 阶段 7 坏存档恢复

### 7.1 恢复界面与选项①②

- **目标**：坏存档出现时不覆盖，玩家可以下载副本，或在内存中继续。
- **产物**：`src/persistence/recovery.ts`（恢复状态：`raw`、`lockPrimary`）；`src/components/Recovery.tsx`：
  - 绘本口吻说明发生了什么、可以做什么（文案见 design 的文案规范）；
  - 选项①：下载损坏数据副本，Blob 内容为读到的原始字符串，UTF-8；
  - 选项②：用空白数据在内存中继续。`lockPrimary` 保持为真，任何存储键都不写入。顶部持续显示“这次不会收起来”提示与导出入口。
- **验收**：E2E：把 `ub:save` 写成非法字符串后刷新，出现三个选项的恢复界面；`ub:save` 的值与刷新前逐字符相同；选项①下载的文件与原字符串逐字符相等；选项②之后刷新，`ub:save` 仍是原字符串，备份键不存在。
- **依赖**：6.3。
- **需求**：R9.5, R9.6, R9.7, R11.11。

### 7.2 选项③：备份、新空存档与读回校验

- **目标**：只有备份成功且读回一致，才新建空存档。
- **产物**：`src/persistence/recovery.ts` 的 `backupAndStartFresh`，严格按 design 的顺序执行：
  1. `nextBackupKey` 扫描已有键名，取最大序号加 1，绝不覆盖旧备份；
  2. 写入备份键并逐字符读回比对；失败则返回错误，主键不变；
  3. 写入新空存档到主键；写入抛错则尽力还原主键原文，返回错误；
  4. 立即读回主键并逐字符比对；失败则尽力还原主键原文，返回错误，不提示成功；
  5. 只有第 4 步成功才返回 `ok`。

  界面：选项③先弹出确认对话框，取消或 Esc 不写入任何键。只有收到 `ok` 才离开恢复界面，其余结果都停留在恢复界面，显示 design 中对应的温柔文案，选项①②仍可用。
- **验收**：P16（备份失败时主键不变）、P17（写入顺序：备份写入与读回先于主键写入）、P18（备份逐字符相等，且不覆盖旧备份）、P20（新存档读回一致才算成功）通过；选项③取消时没有任何写入。
- **依赖**：7.1。
- **需求**：R9.5, R9.8, R9.9。

### 7.3 坏存档 E2E 矩阵

- **目标**：用自动化覆盖各种坏存档与各种写入失败。
- **产物**：`e2e/recovery.spec.ts`，覆盖四种坏存档输入：非法 JSON、`schema_version` 为 2、超长字段、重复 Slot。每种都进入恢复界面。写入失败用 `page.addInitScript` 在测试中包装 `localStorage.setItem`，不改产品代码，覆盖：备份写入失败、备份读回不一致、主键写入失败、主键读回不一致。
- **验收**：每种情形的断言符合 R9.5 至 R9.9；页面打开阶段对主键与备份键的写入次数为 0（P12 的恢复部分与 P17 的启动部分）。
- **依赖**：7.2。
- **需求**：R9.5, R9.6, R9.7, R9.8, R9.9, R9.11。
